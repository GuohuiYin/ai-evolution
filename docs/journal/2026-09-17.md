## K8s 无 uvx 问题收口：MCP fetch 独立工作负载 + Streamable HTTP（ADR-0016 观察项结案）

- **方案裁决过程**：Owner 追问"业界标准做法"——查证后共识清晰：stdio 是桌面/单客户端
  协议（实测 20 并发 22 请求挂 20 个），部署态现行标准是 Streamable HTTP；存量 stdio
  服务器用 gateway/proxy 适配层桥接是通行做法；ToolHive/kmcp 这类 operator 控制面要
  "多团队重复写 YAML"的拐点之后才值得。据此把昨天的 sidecar 建议修正为**独立
  Deployment + Service**（业界更主流的形态）
- **选型实测推翻两个候选**：mcp-proxy（Python 桥）最新版与现行 MCP SDK 不兼容（import 即炸）；
  fastmcp 4.x 移除了 as_proxy API。最终钉 `fastmcp==2.14.7` + `mcp-server-fetch==2026.8.18`，
  本地 initialize + tools/call 真实抓取全通后才进 Dockerfile
- **落地形态**：`k8s/mcp-fetch/`（Dockerfile + 15 行 proxy.py 桥）+ `k8s/mcp-fetch.yaml`
  （Deployment/Service/NetworkPolicy 只收入向——fetch 出向任意 URL 是职责本身，
  做不了域名级收口，诚实注释而非假性安全）；应用侧 `application.yml` 传输按 profile
  分文档（default=stdio 本地零变化，k8s=HTTP 连 Service DNS），连接键 fetch 不变，
  `McpClientToolConfiguration` 上层零感知（契约不变式）
- **集群冒烟抓获的坑**：minikube 同 tag 镜像 `image load` 静默不更新（pod 一直在跑旧镜像，
  uvx 崩溃循环），`docker save` 出 tar 再 `--overwrite` 载入才换成功——**部署清单同 tag
  重建时必须核对运行时镜像 digest**，已记入 k8s 操作经验
- **端到端验收**：双 rollout 就绪；鉴权回归三场景（health 200 / chat 无 key 401 / mcp 无 key 401）；
  agent 持证经 HTTP 桥真实抓取 example.com，6.6s 返回，tool-audit 记录
  `tool=fetchWebPage outcome=success`（traceId=b24cbd16 串联）；`./mvnw verify` 全量绿
