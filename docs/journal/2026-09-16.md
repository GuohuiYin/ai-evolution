- **#3b 固定窗口实现**（`ed7db9b`）：每身份每分钟 N 次（`ai.security.rate-limit.per-minute: 60`）。
  关键决策：限流排在鉴权**之前**（顺序 TraceId → 限流 → 鉴权）——撞库/无凭证试探按 IP 记账，
  401 不是免费通道；持证按 key 记账且不落日志（防泄漏）。429 + ProblemDetail + Retry-After
  （距下一窗口秒数，客户端可自我节流）。时钟构造器注入，窗口翻转单测不靠 sleep；
  OpenAPI 经 OpenApiCustomizer 给全端点横切补 429 声明（A7 全部错误码，不逐控制器手抄）

  真实冒烟：错误 key 连发 65 次，前 60 次 401、第 61 次起 429 + Retry-After=29（阈值翻转实测）；

## 当日追加三：W12 #4 模型自动降级（裁决=做，验收抓获两个真缺陷）

- **裁决**：本周做。触发条件早已成熟（能力地图挂账"双模型配置在，无自动降级链路"），
  且 #2/#3 把安全面收口后韧性是本周主题的自然延伸
- **#4a 装饰器**（`368db4b`）：`FailoverChatModel` 实现 ChatModel，标 @Primary 后全工程注入点
  （对话/分析/judge）零改动获得降级能力。切换判据单点 `isFailoverWorthy` 沿 cause 链识别：
  TransientAiException（5xx）/ResourceAccessException（超时/IO）切；NonTransientAiException
  （4xx，请求/账户语义问题）不切——402 余额不足应直接报警而不是悄悄烧备用额度；
  流式只在首 token 前允许切换（已吐内容重放会造成重复输出）
- **#4b 接线**（`2599dbd`）：备用 Qwen3.5-35B-A3B 走 SiliconFlow，复用 embedding 同一份
  `spring.ai.openai.*` 凭证，零新增密钥面（A5）。**坑**：凭证必须落在 OpenAiChatOptions 上——
  OpenAiChatModel.Builder.build() 会用 options 的 baseUrl/apiKey 补建 async 客户端
  （OpenAiSetup.setupAsyncClient），手工组装 ClientOptions 传给 sync 侧会导致 async 侧
  无凭证、启动即炸（jar 层反编译核实，探针测试逐步缩小定位后已删）
- **#4c 故障注入验收**（`c9cfe5a`）——**这是今天最有价值的环节，抓到两个单测盲区缺陷**：
  1. `ClassCastException: DefaultChatOptions → DeepSeekChatOptions`：ChatClient 装配从
     `ChatModel.getOptions()` 取默认选项，接口默认实现返回通用 DefaultChatOptions，
     而 DeepSeek/OpenAi 的 createRequest 都把 Prompt.options 强转各自具体类型。
     修法：getOptions()/getDefaultOptions() 均透传主力；降级路径用备用模型默认 options
     重建 Prompt（跨供应商 options 不可复用，javadoc 留痕"未来按请求调参需补字段映射"）。
     **单测 mock 天然绕过此坑**——mock 的 ChatModel 不做强转，只有真实 bean 装配才暴露
  2. 降级被库内重试拖死：Spring AI 默认 10 次指数退避（上限 3min/次），jstack 抓到请求线程
     停在 `RetryTemplate.sleep`——供应商级故障要挂起十分钟级才轮到降级，应急通道形同虚设。
     `spring.ai.retry` 调为 2 次/短退避（1s 起步，上限 5s）：内部重试只盖瞬时抖动，
     供应商故障快速交降级
- **实测结果**：主力指向死端口 → 秒级触发 WARN「主力模型调用失败，自动切换备用模型
  fallback=Qwen/Qwen3.5-35B-A3B」（traceId 串联）→ Qwen 应答 HTTP 200（带 RAG 引用），
  `model.failover.total` 计数器=2。降级期端到端 181s——SiliconFlow 共享算力首 token
  延迟属选型已记录的预期代价（30-60x）
- **明确不做**：降级期间不降质 prompt（完整 RAG 上下文照发）；按请求调参的跨供应商映射
  （当前全链路默认 options，无实际损失）

**本周三个最值得记住的教训**（都进了我自己的"验收才见真章"清单）：

1. **Mock 是双刃剑**：#4 单测 9 条全绿，但真实装配立刻炸出两个缺陷——ChatClient 从
   `getOptions()` 取默认选项（接口默认实现是通用 DefaultChatOptions，两个模型的
   createRequest 都强转具体类型），以及库默认 10 次指数退避把降级拖成十分钟级挂起。
   装饰器/装配层改动必须配一次真实冒烟，单测绿不等于链路通
2. **官方 SDK 的构建器有隐藏职责**：Spring AI 2.0 的 OpenAiChatModel.Builder 会用 options
   里的凭证补建 async 客户端——手工组装 ClientOptions 绕过了这条契约（#4b 坑）
3. **安全面的放行清单一进场就是共享资源**：#3 限流若复制 #2 的放行清单就是 A11"两次即收口"
   的教科书触发点，先提取 SecurityAllowlist 单点再动手

**本周顺带消除的隐患**：eval-generation.yml 补 MCP 关闭 + 临时 key（CI 无 uvx 会起不来）；
Qdrant 容器退出导致应用启动失败时，报错链路清晰可追（bean 依赖树完整打印）。

**遗留观察项（非阻塞）**：K8s 部署时 MCP Client 需镜像装 uv 或 `AI_MCP_CLIENT_ENABLED=false`；
