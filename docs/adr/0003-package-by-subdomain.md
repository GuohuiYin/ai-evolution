# ADR-0003：按子域分包，拒绝技术分层横切

- 日期：2026-09-05
- 状态：已接受（Owner 确认）

## 背景

W5 中期 `chat` 包膨胀到 16 个文件，Owner 提出按技术类型细分（api/model/service/exception 子包）以便阅读管理。

## 决策

1. **域内禁止按技术类型横切**。包的第一职责是表达"什么会一起变"，类型信息由命名后缀与 IDE 承担；技术分包会把一次功能变更的相关文件拆散到多个目录，并给"技术分层思维"回潮开口子。
2. **按子域拆分**：`analysis`（个股分析能力）与 `prompt`（prompt 资产库，chat 与 analysis 的共享内核）从 `chat` 独立。异常类跟随其语义所属域（`InvalidPromptVersionException` 归 prompt，因其表达"prompt 资产版本不存在"）。
3. **子域划分前置到设计时**：新能力在开发之初即判断是否独立子域并建包，不等域内文件过载后再被动拆分（Owner 明确要求）。

## 备选方案与争论点

- 技术类型子包（api/model/service/exception）：阅读查找直观、对 Java 传统开发者熟悉，但优化错了维度（按类型查找而非按功能变更），且异常收容所式分包会切断异常与领域的联系。否决。
- 维持域内扁平不做任何细分：小域可行，但 chat 的 16 文件已证明会拥挤，且混合了对话与分析两个独立变化原因的能力。否决。

## 后果

- 包结构：`chat`（对话：RAG/Agent）、`analysis`（个股分析）、`prompt`（prompt 资产）、`rag`（知识检索）、`stock`（数据源）、`tool`（工具层）、`eval`（评估）
- AGENTS.md A9 修订为"子域前置拆分"（v1.6）
- ArchUnit 规则（B2）落地时按此包结构定义依赖方向
