# ADR-0018：语言策略——Java 承载在线编排，Python 承载离线实验，MCP 做层间边界

- 状态：已接受
- 日期：2026-10-20

## 背景

项目演进中持续遇到"这个能力用什么写"的选择：造数脚本、embedding 实验、新检索算法验证用 Python 生态最顺手；在线检索编排、API 网关、评测调度则长在 Java/Spring 体系内（ADR-0001 技术栈、ADR-0006 手工编排、ADR-0009 MCP 暴露）。此前按直觉各写各的，没有成文边界，存在两个风险：一是在 Java 里硬复刻 Python 已有生态（评测框架、数据处理），二是离线 Python 脚本无约束生长成第二个无人维护的生产系统。需要一条显式语言策略。

判断维度（按重要性）：AI 生态成熟度 > 与存量系统集成成本 > 团队技能 > 工程化能力 > 并发模型 > 部署运维。性能不构成决策因素——Agent 延迟被 LLM 的 TTFT/TPOT 支配，语言运行时差异可忽略。

## 决策

1. **在线侧 Java**：检索编排（ADR-0017 两段式）、ReAct 研究循环（ADR-0015）、API 网关、权限、评测调度（ADR-0007）——一切长生命周期、需稳定性审核、需接存量微服务的代码，留在 Java/Spring 体系。
2. **离线侧 Python**：造数、chunking/embedding 实验、新检索算法（BM25 参数、RRF 变体、reranker 选型）的验证原型。验证通过后二选一：回移植 Java，或封装为独立服务。
3. **层间用 MCP/脚本边界解耦，不用进程内混编**：模型侧能力按 ADR-0009/0016 的 MCP 路线暴露与消费；一次性实验保持脚本形态，不进 Java 主仓构建链。
4. **禁止事项**：不在 Java 侧复刻 Python 已有成熟生态（如 LLM-as-a-Judge 打分器若 Python 实现更优，走 MCP 而非移植）；不让 Python 离线脚本直接面向在线流量。

## 备选方案

- 全栈 Python（LangChain 体系重写）：AI 生态最齐全，但在线侧稳定性体系、存量集成、团队工程化纪律全部重置。否决。
- 全栈 Java（一切用 Spring AI/LangChain4j）：新框架滞后 Python 生态 6~12 个月，实验迭代速度被拖累。否决。
- TypeScript 交互层：当前无 C 端流式 UI 需求；若未来长出实时交互产品形态，重评 Vercel AI SDK 路线。

## 后果

- 正：每种语言只做自己生态最强的事；实验速度不被 Java 工程纪律拖住，在线稳定性不被实验代码污染；MCP 边界同时解决语言异构和工具治理。
- 负/权衡：双语仓库需要两套工程规范（Python 侧至少要有 lint/依赖锁定）；回移植路径存在重复劳动，接受为探索成本。
- 待办：Python 离线脚本的工程规范（目录归属、依赖管理）首次引入时成文。
