# ADR-0011：红线服务端校验第一版只告警不拦截

- 状态：已接受
- 日期：2026-09-08（W7-Step1 P1，红队基线 P1 项落地）

## 背景

红队基线结论：买卖建议拦截（红线 02）目前完全依赖"system prompt + 模型自觉"，服务端零校验。间接注入 n=2 未打穿不能定论，需要服务端兜底检测。

## 决策

1. **检测单点化**：`RedLineGuard`（compliance 域）统一持有买卖建议模式；模式按"建议类词→操作词"语序设计，拒答话术（"不能给出买入建议"）语序相反天然不命中——误报控制是检测器的第一设计约束（告警疲劳比漏报更致命）。
2. **执行点 AOP**：`RedLineAuditAspect`（chat 域）切 `ChatService.chat(..)` 接口方法——三个对话服务实现（Rag/Agent/Routing）全覆盖，新增实现自动获得检测（开闭原则）。
3. **只告警不拦截**：命中打 `stage=REDLINE_HIT` WARN 日志（traceId 串链），响应原样返回。先积累真实命中数据，误报率有数据支撑后再议硬拦。

## 备选方案

- 命中即拦截改返回拒答话术：正则检测存在理论误报面，误拦合规回答比延迟发现代价高。否决（留作有数据后的升级路径）。
- 用模型做输出审查（LLM-as-judge）：成本高延迟大，现阶段过度设计。否决。

## 后果

- 正：红线防线从"模型自觉一层"变"模型自觉 + 服务端检测两层"；告警与请求链路同 traceId，命中可回放。
- 负：正则检测对变形表述（拼音/谐音/拆字）无效——已知边界，防御纵深留给后续（输出侧 judge 模型是候选）。
- 伴随变更：`AgentChatService` 实现 `ChatService` 接口（切面覆盖前提）；`ChatController` 改为注入具体类 `RoutingChatService`（/ai/chat 语义即"路由对话"，比接口+@Primary 更直白，同时消除切片测试歧义）。
