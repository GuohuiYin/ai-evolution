# W11 计划：查询改写 + 多轮评测集 + 生成 eval CI 回归门

> 对应 M3 阶段索引 W11 行。主题：让多轮对话"查得到、测得出、防得住"。

## 背景（为什么做）

W10 #0c 冒烟实锤（证据 #4）：首轮"茅台的酿造工艺"（hits=5）→ 追问"其中的 12987 是什么含义"
检索 hits=0 硬拒答。记忆 advisor 只解决了模型侧上下文，**检索拿原始追问去向量化**——
查询改写是多轮 RAG 的咽喉。同时多轮能力必须有自己的评测集，否则改写效果无度量（A14 对账挂账项）。

## 任务分解

| # | 任务 | 验收条件 |
|---|---|---|
| 1 | **查询改写器**（TDD）：`QueryRewriter` 接口（IOP）——基于会话历史把追问改写为自足查询（如"其中的 12987"→"茅台 12987 工艺的含义"）；DeepSeek 实现 + 直通实现（首轮无历史不改写，零成本直通）；检索侧改走改写后查询 | 单测：追问改写含主语补全 / 首轮直通零调用；冒烟：证据 #4 场景复测，追问检索 hits>0 且回答命中 12987 工艺 |
| 2 | **多轮评测集**：生成黄金集新增 `multi-turn` 类别（指代消解 / 追问深化 / 话题切换 ≥6 条），含多轮对话脚本（先问 A 再问"它…"）；eval Runner 支持按脚本顺序同会话执行 | 新用例进 golden-set-generation（先登记 changelog 再提交）；改写开启/关闭两轮跑批对比入报告 |
| 3 | **生成 eval CI 定时回归门**：GitHub Actions 定时任务（如每日）跑生成黄金集，类别均分阈值告警；repo secrets 由 Owner 配置 | workflow 文件入仓 + 一次成功运行记录；失败时 issue/通知可见 |
| 4 | **HyDE/查询扩展评估**（能力地图挂账项）：调研论证是否引入，不动代码 | 结论写入能力地图（采纳 → 挂 W14+；不采纳 → 记录 why-not） |

## 明确不做

- 不改混合检索/rerank（W13 的事）
- 不做查询改写的缓存优化（先正确后快）
- CI 门只做定时回归，不做 per-commit 阻塞（真实 API 噪声，A13 纪律门仍是 per-commit 防线）

## 顺序与节奏

1 → 2（改写先于评测集，评测集用来裁决改写）→ 3 → 4。每天 1 项，逐项 review。
