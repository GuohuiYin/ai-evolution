## 四、注入定位计时实录（SOP 实战）

**注入一（Qdrant 停服，检索层）**：发现 ~1 分钟（检索依赖通路 500、纯工具通路 200，
横切隔离现象典型）→ 按 SOP 落到「外部资源层」→ `docker ps` 证实容器停止，
**定位 ~2 分钟**。SOP 对照表「现象 → 层 → 仪器」链路走通。

**注入二（DeepSeek 断流，模型层）**：与熔断二自然撞线**同时叠加**，是最困难的一种
形态——预算闸在调用链上位于模型层之前，断流期间请求根本没打到模型，byModel 无
Qwen 痕迹。12:23 报障 → 12:26 双事件各自定位（熔断看台账撞线，断流靠重启后
failover WARN 证实），**定位 ~3 分钟**。两案均远低于 30 分钟目标，SOP + 可观测
设施（台账/四级日志/traceId）组合有效。

## 六、Failover 观测（本窗口最大架构发现）

1. **切换本身正确留痕**：WARN 带 fallback 目标、errorType、原始错误、traceId，
   「failover 是事件而非正常」的识别目标达成。
2. **failover ≠ 高可用**：备模型 Qwen 是 thinking 模型，生成 3,025 token 耗时跑穿
   planner 活动 120s 的 StartToClose 超时预算（`ResearchPipelineWorkflowImpl`），
   pipeline 两笔 241s 处 500。**主备模型延迟特征差异会撞破编排层时间预算**——
   切换保住了「有回答」，保不住「在时限内回答」。
3. **JVM DNS 缓存阻断自愈**：12:34 hosts 已恢复，但应用在 12:27 断流期间启动，
   JVM 把 127.0.0.1 缓存住，此后 13 分钟全部走 Qwen，直到 12:47 重启才恢复主力。
   「依赖恢复 ≠ 应用恢复」。
4. **主备双失瞬间存在**：12:43:15 一笔 502（主力连接拒绝 + Qwen 瞬时失败），
   说明 failover 只防得住单点。

## 八、HITL 与负向产出

**HITL 挂起观测到 5 次**（10:38、10:43、11:32、11:55、11:57）：同一追问句
「它 2024 年的净利润是多少？」触发审批，无人值守下 10 分钟超时后 fail-closed，
返回「经多轮独立复核仍无法满足溯源与合规要求，本次不予作答」，延迟 669–719s
（= 600s 超时 + pipeline 开销）。行为正确，但**无人值守场景下 HITL 必然全部
转化为 10 分钟延迟 + 拒答**，产品层面需要「无人模式」策略（见 S7）。
