# 进阶期下半场我误解过什么（W25-W27 复盘）

> 接续 [w14-w24-misconceptions](w14-w24-misconceptions.md)（#1-13）。
> 同口径：每条误解 = 曾经的假设 → 实证证据 → 修正后的认知；不写成绩总结，只写认知修正。
> 2026-11-03 成文（W25-W27，#1-7；案 30 挂账归因结案后转入正册 #7，挂账节清空）。

## 1. "装上 failover，模型层高可用就有了"

- **曾经以为**：FailoverChatModel 兜底供应商瞬态故障（W12 故障注入实测定参），降级链路演练过，
  模型层韧性闭环。
- **实证**：W26 无人值守窗口 failover 首次真实点火——DeepSeek 断流下 Qwen 承接了流量
  （台账 105K token），但 pipeline 两笔在 241s 处 500：planner 活动 120s 超时预算是按
  DeepSeek 延迟特征定的，Qwen thinking 单轮生成 3,025 token 直接跑穿。**切换成功了，服务还是断了。**
- **修正**：failover 解决「供应商单点」，不解决「时间预算匹配」——主备模型的延迟特征是
  编排层超时预算的输入参数，换臂必须连带评估超时配置（挂账 W28+：failover 超时联动）。
- 证据：[w26-unattended-run-report](../ops/w26-unattended-run-report.md) §六.2（P2，2026-11-02）

## 2. "熔断器装在哪不重要，fail-closed 就行"

- **曾经以为**：预算闸挂链首、fail-closed 拒答，是零副作用的纯安全收益。
- **实证**：W26 双故障叠加——预算闸在模型层之前，DeepSeek 断流注入期间请求根本没打到模型，
  byModel 无 Qwen 痕迹，断流被熔断**隐身**；双事件各自定位靠重启后对照才切开（~3 分钟，
  有运气成分）。**熔断器的位置决定它遮蔽什么。**
- **修正**：熔断/闸门的链路位置是观测性设计决策——前置熔断省成本但遮蔽下游故障信号；
  双故障叠加预案里「各自定位」必须前置演练，故障注入不能只注单点。
- 证据：同报告 §四（P3）

## 3. "参照腐烂只有语料演进一型"

- **曾经以为**：参照答案的寿命挂在语料上（W19 F4 法定代表人真值反转、W26 v3.3 一季度案翻案，
  均为语料演进掀翻参照前提）。
- **实证**：W27 校准收卷案 14——「那 600519 呢」参照写 1558.00/1525.00，tushare 实返
  1525.00/1524.00（2026-11-03 API 复核留痕）。被测回答全对，被 judge 按腐烂参照判 0 误杀。
  腐烂源不是语料，是**数据源切换**（W26 mock→tushare 换源）后参照未同步。
- **修正**：参照答案的寿命 = min(语料, 数据源, 世界状态)——凡外部依赖切换（语料轮换 /
  数据源换源 / 口径变更），参照重锚清单必须同步过一遍。第二型登记 changelog v3.4。
- 证据：[w27-judge-calibration](../eval/generation/w27-judge-calibration.md) 行动项 1（已结案）+ [golden-set-changelog v3.4](../eval/golden-set-changelog.md)

## 4. "证据包按单轮设计就够"

- **曾经以为**：pipeline 证据包（检索片段 + 工具数据）完备覆盖复核所需，多轮是会话层的事。
- **实证**：W27 #2——多轮追问案系统性失分（multi-turn 均分 5.0）：build 检索不带改写
  （「它」无法消解）、review 证据包不含会话历史。修复（证据包入 L2 记忆 + 检索改写装饰器
  接入 pipeline RAG 通路）后 5.0→5.7。
- **修正**：任何按单轮设计的上下文契约都默认欠多轮的债——证据契约、prompt 契约、评估契约
  三处都要显式回答「多轮时怎么办」；新增跨域依赖（loop→rag）必须显式登记（ArchUnit 白名单）。
- 证据：[w27-multiturn-context-fix](../eval/generation/w27-multiturn-context-fix.md)（2026-11-03）

## 5. "fail-closed 覆盖了故障防御"

- **曾经以为**：拒答向失败（fail-closed）是故障的终极兜底姿态。
- **实证**：W27 #3a——生成 eval 长跑批一个案子挂死（模型 HTTP 无 response 超时），
  整批 58 案陪葬。fail-closed 防「错误放行」，对「永不返回」零防御。
- **修正**：故障形态至少三种——错答、拒答、挂死；fail-closed 只覆盖前两种。一切外部调用
  必须有超时上界（connect 10s / response 3min 入共享配置），一切长跑批必须单案故障隔离
  （失败单列、不毁整批、退出码非零）。
- 证据：`5303591`（GenerationEvaluator 单案隔离 + ModelHttpTimeoutConfiguration，2026-11-03）

## 6. "自己写的运行报告就是事实"

- **曾经以为**：W26 运行报告「预算闸内存计数、重启清零可被绕过」（P4）是窗口内实测结论。
- **实证**：W27 #4 开工前代码核验推翻——预算闸从 W25 #2 起每次调用实时读 JSONL 台账聚当日
  用量，重启不丢；报告自己的数据也自证（二次撞线 501 万含重启前 140 万，重启并未清零）。
  P4 系故障窗口里凭记忆落笔的误记，已勘误回写。
- **修正**：观测文档也会腐烂——故障窗口里凭印象写下的机制性断言，事后必须与代码做一次
  显式核验再归档；「本次窗口内实测」的标注不能替代核验。
- 证据：[w26-unattended-run-report](../ops/w26-unattended-run-report.md) P4 勘误（2026-11-03）

## 7. "缺陷冒头，罪魁就是最近上线的新机制"

- **曾经以为**：案 30（茅台法定代表人）r3 批回退 6→2，嫌疑直指 W26 v3.3 的 asOf 优先重排——
  最新上线的机制置顶了 2025 年报片段，引入实体层级混淆，「看上去就是它」。
- **实证**：单案双跑对照（asOf 开/关）两轮回答与检回 5 块集合完全相同，重排嫌疑排除；
  向量库直查发现正确答案块（「公司的法定代表人 陈华」，2025 年报 + 2026 半年报各一块）**在库**，
  真实嵌入直查仅排第 15/16 名——「上市公司的法定代表人」与「控股股东的法定代表人」语义高度同质
  （score 挤在 0.65~0.71 窄带），正确块进不了 top-5 候选池。真因是**检索召回漏检**，
  模型的「资料未覆盖」反而是诚实的 grounding 行为；asOf 重排若拿到候选池反而会把
  2026-06-30 最新块顶上来——它是解药不是病因。
- **修正**：归因要破近因偏差——新机制只是嫌疑名单的第一名，不是结论；先做单变量对照
  （开关双跑）再谈修复。检索质量的瓶颈在召回率而非重排：召回增强（top-k 扩大 / 关键词混合 /
  多路召回）挂账 W28，与检索改写增强合并设计。
- 证据：[w27-judge-calibration](../eval/generation/w27-judge-calibration.md) 行动项 3（2026-11-03 结案）
